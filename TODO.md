## Безопасность

### Критические

- [x] **XSS в `index.js`** — строка с `error.message` исправлена: теперь используется DOM API
  (`replaceChildren` + `createElement` + `textContent`). `contentPanel.innerHTML = html` (строка 95)
  оставлен как есть — HTML приходит от доверенного Django-сервера с автоэскейпингом.

- [x] **Stored XSS в проверке дублей станций** (`station_form.html`, `station_update_form.html`) —
  `s.name` и `s.road__title` из JSON вставлялись через конкатенацию строк + `innerHTML`.
  Атакующий мог создать станцию с именем вида `<img src=x onerror="...">` и угнать сессии других
  участников организации. Исправлено: заменено на DOM API (`replaceChildren`, `createElement`,
  `textContent`).

- [x] **IDOR: медиафайлы без авторизации** (`nginx.conf`, `urls.py`, `views.py`) —
  Nginx отдавал `/media/` напрямую без проверки аутентификации. Файлы доступны по предсказуемым
  путям (`tasks/task_<id>/...`), ID — последовательные целые числа. Любой мог скачать чужие
  вложения без логина. Исправлено: добавлен `ProtectedMediaView` (`LoginRequiredMixin` + защита
  от path traversal), маршрут `media/<path>` всегда через Django; Nginx отдаёт файлы только
  через `X-Accel-Redirect` из внутреннего location `/protected-media/`.

- [x] **Медиафайлы без проверки организации** (`ProtectedMediaView`) — после исправления IDOR файл
  всё ещё отдавался любому вошедшему пользователю, знающему путь: вложение или аватар чужой организации,
  чужая инструкция. Исправлено 07.10.2026: файл получает только тот, кому доступна страница с ним
  (вложение — своя организация и `view_task`; инструкция — у кого она в списке и кто загрузил;
  аватар — сам пользователь и его организация). Отказ — 404.

  Решение: добавить `annotate(task_count=Count('tasks'))` в queryset view,

  Решение: добавить `'comments__user'` в `prefetch_related`.

## На будущее

- [ ] **Блок «Время в статусах» на карточке задачи** — сколько задача провела в каждом статусе.
  Данных `TaskStatusChange` (`from_status`, `to_status`, `changed_at`) и `Task.created_at` достаточно,
  новых полей и миграций не нужно — только расчёт в `BugDetailView`:
  от создания до первого перехода — «Новая»; между соседними переходами — промежуточные статусы;
  от последнего перехода до текущего момента — нынешний статус. Повторные заходы в статус складываются.

  Где данные неполные:
  - задачи, менявшие статус до миграции `0017`: прошлые переходы в историю не занесены,
    известны только дата создания и текущий статус — блок скрывать или показывать «нет данных»;
  - смена статуса через `TaskInline` на странице станции в админке в историю не попадает —
    **закрыть до того, как делать блок**, иначе расчёту нельзя доверять;
  - суперпользователь может удалить запись истории в админке — интервалы исказятся.

  Перед показом проверять непрерывность цепочки: `to_status` предыдущей записи совпадает с `from_status`
  следующей, а `to_status` последней — с текущим статусом задачи. Если цепочка рвётся, расчёт не показывать.
